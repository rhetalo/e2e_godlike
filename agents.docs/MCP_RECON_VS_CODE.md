# MCP-recon vs наш код-формат — практическое сравнение

> Документ про **инструментарий/воркфлоу**, не про конкретную панель. Написан после
> живой MCP-разведки `ultra.panel.godlike.host` (06-Jun-2026) как рабочий пример.
> Цель — чтобы владелец/агент осознанно выбирал инструмент под задачу, а не по привычке.
>
> Конкретные находки той сессии (новые экраны, селекторы, дрейф) лежат **не здесь**, а в
> `agents.docs/game-panel/KNOWLEDGE_BASE.md` и `TEST_PLAN.md` (гибридная раскладка).

## TL;DR

| | Playwright **MCP** | Наш **код-формат** (page objects + `selectors.ts` + specs) |
|---|---|---|
| Что это | Живое управление одним браузером инструментами `browser_*` прямо из чата | Версионируемые TS-тесты, гоняются `npx playwright test` / в CI |
| Сильная сторона | **Разведка, отладка, «пощупать» незнакомый экран** | **Регрессия, повторяемость, CI, чужой ре-ран** |
| Состояние | Эфемерное (сессия чата); refs живут до следующего snapshot | Стабильное (git); селекторы переживают ре-раны |
| Стоимость | Токены чата + лимиты (snapshot’ы большие) | Время на архитектуру, зато потом дёшево гонять |
| Воспроизводимость | Нулевая (никто, кроме текущей сессии, не повторит) | Полная (любой запустит ту же команду) |
| **Вывод** | Фаза **recon/debug** | Фаза **закрепления покрытия** |

**Они не конкурируют — это две фазы одного пайплайна:** MCP щупает живой DOM → находки
оседают в `KNOWLEDGE_BASE.md`/`selectors.ts` → пишется стабильный spec через page object.
Раньше фазу «пощупать» закрывала `live-recon` skill (разовые `tmp-*.mjs`-пробы); **MCP —
её прямая, более интерактивная замена.**

## Как это ощущается в работе (из реальной сессии)

**MCP-цикл (то, что было сейчас):**
1. `browser_navigate(url)` → `browser_snapshot` → читаешь accessibility-дерево с `ref`’ами.
2. `browser_click({target: "e76"})` / `browser_type` / `browser_fill_form` по этим `ref`’ам.
3. Меняется страница — **делаешь новый snapshot** (старые `ref`’ы протухают).
4. Где нужны CSS-классы/id — `browser_evaluate(() => …)` достаёт реальный DOM.
5. `browser_network_requests` / `browser_network_request` — смотришь REST/WS за экраном.

**Наш код-цикл:**
1. (Раньше) `live-recon`: `tmp-probe.mjs` логинится `gameAuth` и дампит DOM в stdout → удаляешь пробу.
2. Селектор кладёшь в `utils/selectors.ts` (с датой-комментом), локатор — на page object.
3. Spec в `tests/game/panel/*.spec.ts` через page object + `expect` в `test.step`.
4. `npx tsc --noEmit` + прогон спека → коммит на ветку.

## Где MCP реально выигрывает (подтверждено сессией)

- **Скорость старта на новом экране.** Открыл `/extensions`, `/upgrade`, `/database` — сразу
  видишь структуру, без написания пробы. Незаменимо, когда экран ещё **не** в `KNOWLEDGE_BASE`.
- **Интерактивная отладка флоу.** Открыть диалог (Tasks → Configure, Edit Server, Create
  Database), снять форму и **закрыть без сохранения** — пара кликов, видно мгновенно.
- **Сетевой слой за один шаг.** `browser_network_requests` показал эндпоинты
  (`POST …/files/folder`, `…/files/trash`, `…/databases/`) и подтвердил, что удаление файла =
  trash (recycle bin), а create БД реально уходит POST’ом и не удаётся. Это объясняет
  «проверять через reload» лучше, чем гадание по UI.
- **`accessibility snapshot` = готовые ассерты.** Роли/тексты/`ref`’ы — то, на что и так целятся
  web-first ожидания. Хорошо для проверки «что на экране».

## Где MCP проигрывает (тоже подтверждено)

- **Нет стабильных селекторов из коробки.** a11y-snapshot **не отдаёт CSS-классы/id** — только
  роли/тексты/`ref`’ы. Для durable-локаторов в `selectors.ts` всё равно нужен `browser_evaluate`
  по DOM (там и нашлись `server__extensions__*`, `edit__server-block__dialog`,
  `backups-list__*`-стиль BEM). То есть «снять селекторы» — это **доп. шаг**, не бесплатно.
- **`ref`’ы эфемерны.** `e76`, `e119` живут до следующего snapshot/навигации. В коде локатор
  стабилен между ре-ранами — в MCP после каждого перехода пере-snapshot.
- **Снапшоты дорогие по токенам.** Полный snapshot тянет повторяющийся каркас (nav, промо-блок
  Free Premium, таб-чипы). На длинной разведке экономнее точечный `browser_evaluate`,
  возвращающий только заголовки/кнопки/инпуты/BEM (так и делалось во второй половине сессии).
- **Захват тела XHR ненадёжен.** `browser_network_request(part:"response-body")` по create-БД
  вернул пусто — пришлось верить UI/консоли. Для точного тела ответа проба на Node/`request`-API
  бывает надёжнее.
- **Ноль воспроизводимости и CI.** Это интерактивная сессия одного агента. Регрессия,
  ночные прогоны, ре-ран коллегой — только наш код-формат.
- **Прод-риск выше при ручном драйве.** Легко случайно подтвердить мутацию. В коде опасные
  действия закрыты явными правилами (не жать Restore/Reinstall/Send Invite/checkout) и
  self-cleaning teardown’ами; в MCP дисциплина держится только на внимании оператора.

## MCP vs `live-recon` skill (обе — фаза разведки)

| | MCP | `live-recon` (tmp-`*.mjs`) |
|---|---|---|
| Интерактивность | Высокая (кликаешь вживую, видишь реакцию) | Низкая (скрипт прогнал → дамп → правишь скрипт) |
| Селекторы (классы/id) | Нужен `browser_evaluate` | Из коробки (дампишь `outerHTML`/атрибуты) |
| Тело сетевых ответов | Ненадёжно | Надёжно (полный контроль `page.on('response')`) |
| Следы | Только чат | Файл-проба — **обязательно удалить** (правило репо) |
| Кривая входа | Нулевая | Надо писать мини-скрипт |
| Когда лучше | «Пройтись руками», отладить клик, увидеть флоу | Снять точные селекторы/JSON-ответы пачкой |

Практичный гибрид: **MCP для «обойти и понять» → `browser_evaluate` (или короткая проба) для
точных селекторов → код-формат для закрепления.**

## Рекомендация для этого проекта

1. **Новый/недокументированный экран, таб, диалог** → начни с **MCP** (или `live-recon`), снеси
   находки в `KNOWLEDGE_BASE.md`, селекторы — в `selectors.ts`.
2. **Отладка флоки/непонятного поведения вживую** → **MCP** (быстрее, чем гонять весь spec).
3. **Покрытие, которое должно жить и гоняться в CI** → **только код-формат** (page object + spec).
4. **Прод-безопасность одинакова в обоих:** read-only по умолчанию; мутации — только
   self-cleaning с гарантированным откатом; пальцем не трогать Restore / Reinstall / Send Invite /
   Update Subdomain / Add Port / Boost-checkout / Request Withdrawal.
5. **Лимиты:** MCP-snapshot’ы жгут токены — на длинной разведке предпочитай точечный
   `browser_evaluate`; полный snapshot — только когда нужна вся структура/`ref`’ы под клики.

## Тех-заметки по MCP (на будущее)

- Логин-форма раскрывается кнопкой-чузером «Through login/password»; затем `input[type=email]`
  (placeholder «Username or Email») + `input[type=password]` + «Login». OAuth «Authorization» →
  `panel.godlike.host/api/v2/whmcs/login` (вне scope).
- **Shepherd-тур — 6 шагов, всплывает на КАЖДОЙ навигации** («Skip for now»). В MCP гасишь руками
  каждый раз; в коде это делает `GamePanelBasePage.open()` → `ShepherdTour.dismissIfPresent()`.
- `networkidle` на страницах сервера **не наступает** (websocket-консоль + чат-виджет) — навигацию
  не вешать на него.
- API панели: `panel.godlike.host/api/v2/servers/{uuid}/…`, Bearer `ptlc_*` (Pterodactyl client
  token) в заголовке Authorization. **Токен в доки/логи не копировать.**
- Артефакты MCP (`.playwright-mcp/*.yml`, `console-*.log`) — мусор сессии, в git не коммитить
  (проверить, что покрыто `.gitignore`).
