## 2. Применимо к написанию тестов (actionable сейчас)

- **п73 — вставлять реальные TS-сигнатуры в промпт.** При генерации нового PO/компонента
  сначала подтягивать сигнатуру `BasePage` / `VpsPanelServerPage` и генерить строго под
  неё → код компилируется с первого раза (~90% vs ~50%).
- **п65 — явное условие завершения.** Для задач «допиши покрытие» задавать stopping
  condition («зелёный tsc + конкретный spec — стоп»). Иначе агент бесконечно «улучшает».
- **п66 — нумерованные шаги вместо „сделай всё“.** Это и реализует скилл `spec-to-testplan`;
  для ad-hoc задач формулировать шагами.
- **п63 — few-shot для редких паттернов.** Для iframe/Stripe, throttling-webhook показывать
  эталон в промпте — снижает кривые tool calls.
- **п54 — context poisoning.** Если агент получил кривой результат и не исправил явно —
  ошибка «отравляет» все дальнейшие решения. Симптом: повторяет одну ошибку. Лечение —
  `/clear` или явная коррекция. (Знать как «оператору».)

## 3. Evals / тестирование агентного output (раздел 9) — направление на будущее

Чего у нас нет; ложится на QA-мышление напрямую. **Внедрять только когда агент станет
частью прод-пайплайна** генерации (контент/локаторы/баг-репорты в CI) — не ради внедрения
(п1: «добавляй фреймворк, когда почувствуешь боль»).

- **п78/п82 `viteval`, п81 `promptfoo`** — Vitest-style тесты для LLM-вывода:
  `expect(score).toBeGreaterThan(0.8)`, `expect(output).toMatchSchema(...)`. Регрессионная
  защита промптов в CI.
- **п84 Golden dataset** — `input + expected + допустимая вариативность`, ≥50 примеров,
  в git. QA-аналог «эталонного набора кейсов».
- **п85 Trace-based evals** — оценивать *путь* агента (лишние ли tool calls, верный ли
  порядок), не только финал. Полезная оптика при ревью моей работы.
- **п87 Regression CI** — eval-suite на PR, меняющий CLAUDE.md / `.claude/commands` /
  промпты; fail при score < threshold.

> Статус: backlog-идея. Триггер для старта — «агент в CI как генератор артефактов».

## 4. Ведение доки и контекста

- **п51 CLAUDE.md < 200 строк** — чем длиннее, тем хуже агент следует правилам. Детали →
  в `agents.docs/`, в CLAUDE.md только контракт + ссылки. Правило: «правило не нарушалось
  3 месяца — удали».
- **п58 Структурированный resume-state в файле** — надёжнее auto-memory для критичного.
  У нас закрыто скиллом `checkpoint` + HANDOFF.md + `game-panel-next-focus`.
- **п70 Итеративный рефайнинг прямо в доку** — сработавшую формулировку сразу фиксировать.
  У нас = auto-memory + CODE_REVIEW.md.
- **п53 / п96 `/compact` проактивно** — каждые ~50 turns или при деградации качества; не
  ждать переполнения context window.

## 5. Hooks / безопасность (раздел 2) — особенно под live-prod

- **п11 PreToolUse hook: блокировать опасные операции ДО выполнения.** У нас есть только
  PostToolUse (lint). Идея: хук, который блокирует Bash/Write при признаках деструктива
  (rebuild/delete/order без env-gate). **РЕШЕНО НЕ ДЕЛАТЬ (17-Jun-2026).** Профиль риска
  мягче, чем казалось: акк и сервера — тестовые и восстановимые (снести/переустановить),
  состояние между прогонами уже закрыто serial + `afterAll`-recovery + env-gate, и есть
  human-in-the-loop (агент показывает план, auto-permission всплывает). Широкий блок = больше
  friction, чем пользы → safety theater. **Триггер пересмотра:** появление агента-в-CI
  (headless, без человека в петле) — вот тогда машинный стоп окупается (некому нажать отмену).
- **п18 Минимальные права субагенту** — агенту для код-ревью не давать Bash и т.п.
- **п30 Prompt injection через данные** — косвенно: пользовательский контент из панели,
  попадающий в контекст, — теоретический вектор. Низкий приоритет, но знать.

## 6. Что сознательно пропускаем (не наш кейс)

- **Раздел 1 (фреймворки oh-my-claudecode/superpowers/BMAD/gstack)** — для greenfield-
  разработки фич, не для QA-репо.
- **Раздел 4 (headless `claude -p`, microservices, GitHub Actions-агенты)** — релевантно
  только если встроим агента в CI как воркера. Пока CI = обычный Playwright-прогон.
- **Раздел 5 (субагенты / fan-out / worktrees)** — пригодится для массовых рефакторингов
  (напр. разнести raw-локаторы по 8 legacy-спекам параллельно). Инструмент для крупных
  migration-задач, не для повседневных тестов.
- **Раздел 8 (Zod / structured output) и Раздел 10 (RTK/LLMLingua/prompt caching)** — для
  тех, кто пишет агентов программно или платит за API напрямую. Кроме п95 «модель под
  задачу» — у нас уже зашито в `effort-adaptation`.
