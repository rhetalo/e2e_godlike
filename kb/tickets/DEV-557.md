# DEV-557 - Jar больше 100 МБ без вердикта

> **В двух словах.** Сервис mod-scan-service, который решает, какой мод клиентский, не разбирал jar больше 100 МБ
> (Cobblemon Fabric 131 МБ) - это наша находка [DEV-492/F2](DEV-492.md#находки). Фикс !7 поднял лимит до 256 МиБ,
> но только как значение по умолчанию в коде. QA 22-Oct-2026 на проде: **FAIL**, на проде по-прежнему лимит ~100 МиБ.
> 23-Oct-2026 задача закрыта владельцем: DevOps переписал сервис (!8-!11) и перепроверяет лимит сам.

## Что изменилось
- [mod-scan-service!7](https://git.godlike.ovh/panel/mod-scan-service/-/merge_requests/7): дефолт `MAX_JAR_BYTES` 100 → 256 МиБ
  в `internal/config/config.go`. Влит и выкачен 15-Oct-2026. `docker-compose.yml` и `.env` живут только на сервере сервиса, в репо их нет.
- mod-scan-service !8-!11 (23-Oct-2026, Сергей): парсер v6, определение стороны для Forge (режим observe), скачивание jar
  потоком во временный файл (DoD п.2 «память не растёт с размером jar» закрыт по коду), пропуск большого jar до скачивания
  с Warn «jar exceeds size limit» и счётчиком `skipped_oversize`, бюджет на цикл.
- Лимит дочитки при установке на стороне панели (32 МБ) не менялся, так задумано.

## Как это работает
- Обход серверов раз в сутки, ~10:35-11:16 UTC (21-Oct: 57 435 jar). Результат пишется в `minecraft_mod_scan_results` (panel DB).
- При ошибке скачивания сканер пишет только Warn «download failed; skipping file (fail-open)», записи в БД нет.
  Поэтому «нет вердикта» в БД не отличить от «до файла не дошли» - нужен контрольный файл.

## Итог QA
FAIL, 22-Oct-2026, prod.
- [srv:ca326e28](../registry/test-servers.md#ca326e28) (`DEV-557-scan`, Fabric 1.21.1): в `/mods` три файла.
  Контроль 95 МиБ (меньше старого лимита) обход разобрал в 11:03:55 UTC - обход до сервера доходит, нода отдаёт файлы.
  Cobblemon 1.8.2 (133 МиБ, поставлен через Plugins/Mods) и 1.8.1 (131 МиБ) - без вердикта.
- По всему проду за 8 обходов после деплоя ни одна версия Cobblemon Fabric (124-155 МиБ) вердикт не получила,
  хотя пак стоит примерно на 436 серверах (выборка по sha512 с Modrinth API, panel-sql read-only).
- Вывод: работает старый лимит. 95 МиБ проходит, 131 уже нет - это не таймаут (скорость ноды ~70 МиБ/с).
  Вероятная причина: в боевом `.env` явно задан `MAX_JAR_BYTES=104857600` и перекрывает новый дефолт.
- Обход 23-Oct не показателен: после деплоя парсера v6 идёт перепарс всей базы с бюджетом.
