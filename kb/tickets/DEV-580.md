# DEV-580 - бэкап ищется только в рамках своего сервера

> **В двух словах.** Панель искала бэкап по uuid во всей базе и не сверяла его с сервером из адреса запроса. Зная uuid бэкапа
> чужого сервера, со своего сервера можно было скачать архив или дамп базы, развернуть чужие файлы у себя, откатить чужую базу,
> удалить, переименовать или разблокировать чужой бэкап - в обеих панелях (IDOR). Теперь все поиски идут только среди бэкапов
> сервера из роута, чужой uuid отвечает так же, как несуществующий. Попутно починены три ответа 500.
> QA: PASS, prod 30-Oct-2026, все 4 типа бэкапов в обеих панелях.

## Что изменилось
- [panel!1723](https://git.godlike.ovh/panel/panel-godlike-host/-/merge_requests/1723) (бэкенд, влит в master 29-Oct-2026 12:00). Фронт не менялся,
  миграций и env нет.
- v2: `PUT`, `GET …/download`, `POST …/restore`, `DELETE` для `backups/{databases|folders|instances}/{backupUUID}` ищут бэкап только у сервера
  из роута. Роут `instances` обслуживает и бэкапы старой панели (fallback instance → core) - тоже только этого сервера.
- v1 (старая панель): `lock`, `download`, `DELETE` по `/api/client/servers/{server}/backups/{backup}` - то же для всех типов. Бэкап ищется
  до проверки прав.
- Ответ на чужой и на несуществующий uuid одинаковый: v2 400 `No query results for model [...]`, v1 404.
- Попутно: v1 lock бэкапа новой панели 500 → 200; v2 `PUT instances/{uuid бэкапа старой панели}` 500 → 200 (меняет только name и
  is_locked); v1 несуществующий uuid 500 → 404.

## Как это работает
Детали ответов и таблица по типам - [API - backups](../products/up/api/backups.md#поиск-бэкапа-в-рамках-сервера-dev-580).
Модель в репозиториях: `get…ByServerIdAndUuid` / `get…OrNullByServerIdAndUuid`, fallback «инстанс этого сервера, иначе core-бэкап этого
сервера» в одном методе `BackupInstanceRepository` 📖.
