# Bug investigation & report

Цель: довести от симптома до **причины и решения** (фикс теста ИЛИ баг-репорт прода),
без догадок и без флоки-костылей.

## 1. Собрать доказательства

- Точный симптом: что наблюдаем vs что ожидалось (actual vs expected).
- Артефакты: логи, console, network/JSON-ответ, статус-коды, скрин, текст ошибки.
- Воспроизводимость: всегда / через раз (флоки) / один раз. Шаги репро.
- Контекст прода: какой surface, статус сервера, аккаунт, было ли промо/A-B.

## 2. Root cause, а не симптом

- Сопоставь actual ↔ expected. Локализуй слой по флоу (наш стиль — вспомни сегодняшний
  networkidle: причина, а не `waitForTimeout`).
- **Гипотезы, ранжированные по вероятности**, с шагом проверки для каждой:
  ```
  60% — проблема на ноде (Connection refused в ответе) → проверить лог демона
  25% — race condition → повторить N раз, посмотреть тайминги
  10% — кеш/состояние сессии → чистый контекст
   5% — UI/локатор → сверить с live DOM (live-recon)
  ```
- Классификация: **frontend / backend / infrastructure / database / 3rd-party (Stripe, Amplitude, PayPal)**.

## 3. Развилка: чей это баг

- **Тест/локатор/синхронизация** → это наша регрессия: фикс по правилам (`CLAUDE.md`,
  `TEST_GUIDELINES.md`), web-first ожидания, никаких `waitForTimeout`/silent-catch.
- **Баг прода** → не маскировать. Оформить репорт (ниже) и **запарковать** проверку в
  `agents.docs/<surface>/TEST_PLAN.md` («Известные проблемы прода», с датой и кандидатом в баг)
  — как сделано с Databases (400 / Connection refused).

## 4. Баг-репорт — формат (ЖИВОЙ отчёт по корп-шаблону, НЕ Jira-бланк)

Поля бери из **корпоративного Bug Intake** (LIGHT/FULL — см. память `bug-intake-format`,
там настоящие Notion-поля владельца). Пиши как ЖИВОЙ отчёт: заголовки простым русским с
двоеточием, форматированный текст (жирные лейблы + списки), **НЕ код-блок**, без Definition of Done.
Максимум конкретики с РЕАЛЬНЫМИ данными (URL/ID/значения/имена файлов), минимум воды.

**Костяк (по корп-шаблону):**
- **Название бага** — заголовком (h2 `## …`, БЕЗ префикса `Title:`/`Bug Title:`). Коротко и по делу:
  что и где сломано (напр. «Сид-калькулятор: слайдер не меняет тариф — в корзину уходит один продукт»).
- **Где происходит:** раздел/страница + конкретный URL (списком, если мест несколько).
- **Environment:** компактный список тегов — Production; <Ultra Panel / VF-panel / Storefront /
  Billing>; <Minecraft / VPS>. Коротко, без «staging нет».
- **Шаги воспроизведения / Как повторить:** нумерованные, конкретные. Несколько входов →
  «Вариант 1 / Вариант 2».
- **Что происходит сейчас (Фактический результат):** с реальными значениями/ссылками/статус-кодами.
- **Что должно происходить (Ожидаемый результат):**
- **Критичность:** Critical / Important / Minor · **Кто сообщил:** QA — если владелец их ведёт в
  теле (в примерах бывают как свойства карточки — тогда не дублировать).

**По ситуации (ТОЛЬКО при реальной основе — не выдумывать):**
- **Как это обнаружено:** доказательство — конкретные моды/значения/ответы; чем отличается
  рабочий кейс от сломанного.
- **Предположительная причина:** гипотеза ТЕНТАТИВНО («по предварительной информации…»),
  слой (frontend / backend / infra / DB / 3rd-party).
- **Предложение:** конкретная идея фикса, мягко («рассмотреть возможность…»).
- **Дополнительная информация:** тестовый аккаунт, ссылки в админку, примеры «хорошего» и
  «сломанного» сервера/заказа.

**Чего НЕ писать (именно это делает репорт «мёртвым» — обратная связь владельца):**
- Баг НАЗЫВАТЬ надо (заголовком h2), но БЕЗ префикса-лейбла `Title:`/`Bug Title:`.
- НЕ тащить Jira-канцелярит: `Severity/Priority: High/High` с оправданием,
  `Reproducibility: N/M`, `Preconditions:`, `Technical notes for devs`, `PROD (staging нет)`.
  (Критичность пиши одним русским словом по корп-шаблону, а не англ. Severity/Priority.)
- НЕ мешать англ. Jira-лейблы с русским; НЕ оборачивать репорт в код-блок.
- НЕ пояснять очевидное, не оправдывать критичность, не пихать мета-шум (даты recon как тег,
  «Object.is equality», внутряк Playwright).
- Причина/предложение — по делу и тентативно, а не рубрика «для галочки».

## 5. Дальше

- Предложи доп. проверки (что ещё снять, чтобы подтвердить причину).
- Если это блокирует покрытие — отметь в TEST_PLAN, что тест запаркован и почему.
- Не оставляй прод в грязном состоянии после расследования (верни изменённое).
