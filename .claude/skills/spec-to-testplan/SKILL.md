# Spec → Test plan

Цель: из требования получить **проверяемый план покрытия в существующей архитектуре**,
а не сразу код. Финал — план на аппрув (см. `CLAUDE.md` → Implementation workflow).

## 1. Собрать и разобрать вход

Вход: фича / AC / ТЗ / тикет. Выдели четыре корзины:
- **Должно работать** — явные требования (что проверяем позитивом).
- **Не описано / неоднозначно** — дыры в спеке. Здесь **задавай вопросы** (CLAUDE.md → «Ask
  before coding»), не угадывай: окружение, безопасность аккаунта, нужен ли новый `data-testid`.
- **Риски / регресс** — что рядом может сломаться.
- **Пограничные случаи** — пустые/предельные значения, ошибки, права, состояния сервера.

## 2. Не дублировать архитектуру (это #1 провал в этом репо)

Прежде чем планировать новые абстракции — найди существующие:
- тесты: `tests/**/*.spec.ts` (флоу уже покрыт?);
- page objects: `pages/*` (`VpsPanelServerPage`, `GamePanel*Page` — эталоны);
- компоненты: `components/*`; селекторы: `utils/selectors.ts`; фикстуры/утилиты: `fixtures/*`, `utils/*`.

В плане явно укажи: **что переиспользую**, что **расширяю**, и (если нужна новая абстракция)
почему существующую нельзя расширить.

Если экран/таб НЕ задокументирован в `agents.docs/<surface>/KNOWLEDGE_BASE.md` — сначала
**`live-recon`** (снять живой DOM), потом план.

## 3. Построить кейсы

Таблица TC: `id | тип (позитив/негатив/регресс) | проверка | авто или руками | риск`.
- Позитив: основной happy-path по AC.
- Негатив: неверный ввод, отказы, отсутствие прав, валидация.
- Регресс: что ломалось раньше (загляни в `agents.docs/CODE_REVIEW.md`).
- Помечай **что покрывать авто, а что руками** (необратимое/платёжное/визуальное — часто руками).

## 4. Live-prod безопасность (жёстко)

Тесты идут по ПРОДУ, staging нет, аккаунты общие (`CLAUDE.md`):
- Никаких необратимых заказов, спама, действий, способных залочить аккаунт.
- Мутации — **self-cleaning** (создал→проверил→вернул) и в `serial` + `afterAll`-восстановление
  (образец: power/console/config game-panel, vps panel power/rebuild).
- Креды/UUID/URL — из env (`process.env.* ?? fallback`), не в спеке.
- Промо/цены/копирайт меняются — структурные ассерты, не точный маркетинг-текст.
- Не жать Continue/Place Order на оплате; Rebuild/Kill — только с явного разрешения владельца.

## 5. Оформить план

- Папка по домену (`tests/<domain>/`), имя `<feature>.spec.ts`, тег `@smoke/@critical/@regression`.
- Импорт: storefront → `fixtures/base`; панель → `@playwright/test` + page object.
- Перечисли затрагиваемые файлы (page object, selectors-блок, спек) и что в каждом.
- **Жди аппрува перед кодом.** После реализации — `npx tsc --noEmit` + прогон спека.

## 6. Эмитить кейсы в тест-документацию (docs-as-code)

После аппрува плана — оформи кейсы как **Table-test Markdown** в `test-docs/<product>/<feature>.md`
по шаблону `test-docs/templates/test-case.md` (это источник истины по кейсам, см.
`test-docs/README.md`). Для каждого кейса:
- ID `TC-<DOMAIN>-<FEATURE>-NNN` = заголовок теста в спеке (traceability grep'ом).
- «Ожидаемый результат» — как **эффект** (состояние/ответ API), а не текст на экране.
- Поле «Автоматизация» — реальная ссылка на спек; термины сверяй с `test-docs/glossary.md`.
- **Защита от выдумок** (`agents.docs/PROMPT_TEMPLATE.md`): не выдумывай покрытие/селекторы —
  если не уверен, что флоу покрыт, ставь `not-covered`, а для нового экрана сначала `live-recon`.
